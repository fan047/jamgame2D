## 处理方式（全部本地、可复现）

解码链：本机无 ffmpeg、无 Python 音频解码库，使用**无头 Chrome 的 WebAudio** `decodeAudioData` 离线解码预览 MP3，重采样到 48 kHz 单声道，再由 Python 处理。未联网上传任何项目文件，未安装依赖。

处理步骤（两段相同流程，参数不同）：

1. 起始对齐到第一个超过峰值 8% 的采样前 4 ms，去掉前置静音。
2. 按上限截取：碎裂 0.70 s（源 2.500 s），受击 0.15 s（源 1.002 s）；尾部按包络降到峰值以下 40 dB／42 dB 处再留 20 ms，避免把房间底噪拖长。
3. 35 Hz 一阶高通去除预览编码低频隆隆声，保留瞬态主体。
4. 响度对齐旧占位：按 150/700 ms 全段 RMS 匹配旧片的 −23.0／−24.7 dBFS 目标，并设峰值上限（碎裂 0.85、受击 0.60）以免叠加时削波。
5. 1.5 ms 淡入、30／70 ms 平方淡出，量化 16-bit PCM，输出 48 kHz 单声道 WAV（与既有 `AudioImporter` 的 48 kHz / PCM / mono 设置一致）。

## 限制与待确认

- **没有做主观听感验收**：本次只做技术测量与波形检查，无法在游戏中实际播放确认音色是否与画面搭配。请在 Unity Play Mode 或播放上面的组合试听文件后决定；如需更短／更轻／更闷，脚本中 `TARGETS` 的 `max_seconds`、`rms_dbfs`、`peak_cap`、`fade_out` 是集中可调参数。
- 用的是预览 MP3，理论上有损高频损失；两段都很短，实测频谱重心仍在 2.7–4.6 kHz，符合岩石撞击，不影响可辨识度。
- 受击的波峰因数高（26 dB），连续快速受击时峰值会叠加；代码里原有的 0.05 s 节流与 gain 0.3 未改动，若实机听感偏冲，先降低 `peak_cap` 再考虑改代码增益。
- 碎裂 0.7 s 比旧占位长 0.2 s，快速连爆时尾巴会叠在一起；这是有意保留层次，若嫌浑浊就把 `max_seconds` 调到 0.45–0.5 s。
- 未运行 Unity 测试与 Player 构建；Unity 导入后若出现采样率覆盖或压缩设置差异，以 `AudioImporter` 现有设置为准（48 kHz／PCM／单声道）。
